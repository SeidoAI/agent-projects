# tripwire v0.13.1 — residual cutover, recovery ergonomics, scope-clarity, multi-skill

## Context

v0.13.0 converged the session lifecycle on a single executor — schema,
registry, dispatcher, and the central `tripwire session transition`
caller. PM handoffs #5/#6 and the 2026-05-08 issue-triage list
identify the next coherent slice of work: finish the executor cutover,
close the recovery-ergonomics gaps, and address a related cluster of
agent-scope clarity bugs that hit billing-gate today (an agent dropped
a tracked frontend issue from a backend-tagged session because the
spawn prompt reads as identity, not skill-loading).

Six classes of work are bundled here:

1. **WS4-residual.** The dedicated session commands (`complete`,
   `abandon`, `reopen`) and the programmatic callers
   (`pr_watcher_executor`, `monitor_actions`,
   `ui/services/action_service`) still mutate `session.status`
   directly, bypassing `execute_transition`. Six call sites total. Until
   they cut over, the v0.13 "single writer of `session.status`" guarantee
   holds only on the explicit-transition path; the dedicated commands
   keep their pre-v0.13 behavior.

2. **PM handoff #5 Gap B.** The squash-merge orphan-branch problem on
   reopen. The route `paused-to-executing` exists with `preserve_fields`
   declared, but the new `normalise_after_squash_merge` side-effect
   handler that resets the worktree onto `origin/<base>` when its branch
   was squash-merged isn't implemented yet. Gap B is the only PM-handoff
   #5 remedy that isn't already a data-only YAML edit; it needs real
   git plumbing.

3. **PM handoff #6 recovery ergonomics — R3, R4, R6.** Three remedies
   from the 2026-05-08 stuck-loop incident (full text in
   `docs/handoffs/2026-05-08-pm-handoff-6.md` if planted; otherwise see
   the conversation transcript). R3 wants `cleanup` to optionally
   preserve agent-authored uncommitted work; R4 wants `spawn` to handle
   a pre-existing remote branch with commits ahead of base; R6 wants
   `--resume` to be valid from any state where
   `runtime_state.claude_session_id` is populated.

4. **Migration tooling polish.** `tripwire migrate workflow` shipped in
   v0.13.0 but only handles the byte-identical-to-v0.12-template happy
   path and a single force-overwrite escape hatch. Production projects
   that hand-edited their workflow.yaml need a 3-way merge or at least
   a richer diff-and-confirm flow.

5. **Agent-scope clarity.** Four bugs that compound in multi-domain
   sessions: (a) the spawn-prompt's "you are the {skill} agent" framing
   reads as identity rather than skill-loading and causes scope
   self-restriction; (b) issues today carry a single `agent:` field, so
   a session that legitimately bundles cross-domain work has no way to
   declare multiple skill loads; (c) the validator at queue time
   doesn't lint divergence between a session's declared agent and its
   issues' declared agents; (d) the PM-skill's "rationalisations to
   catch" table doesn't list the scope-prune-rationalisation, so the
   PM agent rubber-stamps when an agent silently drops a tracked
   issue. v0.13.1 fixes all four.

6. **PM-agent context priming + scope-rejection workflow.** The PM
   agent today loads the `project-manager` skill on demand. We want the
   skill content **pinned to the top of the PM agent's CLAUDE.md** so
   it's read first every spawn, and we want a **first-class workflow
   step for scope-rejection handling** that mandates writing to the
   inbox (so user-visible escalation isn't optional or buried in
   prose).

Out of scope:

- **PM handoff #6 R1** (bash bg-task 0-byte output capture). This is a
  Claude Code framework problem, not a tripwire problem. Tripwire is
  structurally incapable of fixing it. Track separately at the framework
  level.
- **PM handoff #6 R5** (validate-on-edit hook scope). The hook itself
  lives in `.claude/hooks/` (or a packaged equivalent) and runs full
  `validate_project`. Scoping it to "diff against pre-edit state" or
  "session/issue subtree only" is a hook redesign that lives outside
  the workflow refactor.
- **Multi-workflow runtime.** The eleven non-coding-session workflows
  remain in `docs/workflows/reference-only-workflows.md` as
  documentation. Any one of them becoming runtime-active is a v0.14
  concern.
- **Worktree session.yaml write-locality** (issue-triage #12). The
  bug — `tripwire session transition` writing to the worktree's
  frozen-at-spawn copy of `sessions/<sid>/session.yaml` rather than
  the canonical parent location — needs a project-root resolver that
  walks up from a worktree to the parent. Substantive enough to
  deserve its own slice; **deferred to v0.13.2**.
- **Reopen/rollback audit flag** (issue-triage #5). v0.13.0 makes
  reverse transitions legal as `kind: revert` routes, so the underlying
  capability ships now. The `--reopen`/`--rollback` flag with explicit
  audit semantics is an ergonomics layer that **defers to v0.13.2**.
- **Monitor staleness + JSON parser polish** (issue-triage #13, #14)
  and **queue --promote-issues transactionality** (#17) and
  **verification_unfilled at queue** (#15) — all noted, all
  **deferred to v0.13.2**. None block the recovery-ergonomics work.

## Architectural target

The v0.13 executor diagram from `2026-05-XX-v013-workflow-executor.md`
already captures the runtime shape. v0.13.1 adds:

- **No new architectural surface.** The seven cutover sites all become
  thin wrappers around `execute_transition` (with the route id resolved
  from current+target status, plus per-caller `flags`). The
  `normalise_after_squash_merge` handler is a new entry in the existing
  side-effect registry. R3/R4/R6 ergonomics are CLI-flag additions on
  the existing spawn/cleanup commands. Migration polish is wholly inside
  `cli/migrate.py`.

The result is that after v0.13.1, the executor truly is the sole writer
of `session.status` (no remaining direct-mutation sites), the recovery
flow from PM handoff #6 collapses from 14 manual steps to 2, and Gap B
becomes a one-flag spawn rather than a destroy-and-redo.

### WS1 — Executor extension: caller-resolved route ids + nullable target_status

**File:** `src/tripwire/core/workflow/transitions.py`

Today `execute_transition(project_dir, session_id=, target_status=)`
infers the route from `(current_status, target_status)`. The dedicated
commands need a slightly richer surface:

- Accept `route_id: str | None = None` directly. When non-None, the
  executor looks the route up by id (fail-loud on unknown id) instead
  of resolving from the status pair. Lets `complete_session_cmd` say
  `route_id="verified-to-completed"` unambiguously even when the
  current session is already at `verified` (no ambiguity, but explicit).
- Allow `target_status` to remain optional when `route_id` is supplied;
  derive it from `route.to_ref`.
- When neither is given, raise `TransitionError`.

### WS3 — `normalise_after_squash_merge` side-effect handler (Gap B)

**File:** `src/tripwire/core/workflow/side_effects.py`

Register a new handler:

```python
def _normalise_after_squash_merge_apply(ctx: SideEffectContext) -> SideEffectResult:
    """Reset each session worktree's branch to origin/<base> when the
    branch's PR was squash-merged. Idempotent: a branch already
    matching origin/<base> is a no-op."""
```

Detection: for each worktree entry,
- `git fetch origin` inside the worktree.
- Read the PR state via `gh pr view <branch> --json state,mergeStateStatus,mergeMethod`. If state is `MERGED` and mergeMethod is `SQUASH`, proceed.
- Confirm divergence: `git log origin/<base_branch>..HEAD --oneline` non-empty (the branch has commits that aren't on main).
- On match: `git reset --hard origin/<base_branch>` inside the worktree.

Wire into the `paused-to-executing` and `failed-to-executing` routes in
`templates/workflow.yaml.j2` as a side-effect, conditional on a flag
(`from_squash_merge: true`). The flag is set by `tripwire session reopen`
when the session's PR(s) have already merged on origin (use
`gh pr view ... --json state` once during reopen).

Idempotent and best-effort: declare `idempotent=True` so the executor
doesn't try to invert it. Inverse is unsafe — we'd have to recreate
commits we threw away.

### WS4 — Recovery ergonomics: R3 + R4 + R6 from PM handoff #6

#### R3 — `cleanup --preserve-work`

**File:** `src/tripwire/cli/session.py:cleanup_session_worktrees` (1266–1391)

New flag `--preserve-work`. When set, before removing each dirty
worktree:

1. Compute the diff: `git status --porcelain` inside the worktree.
2. Partition modified files by path-prefix into:
   - **Agent-authored** (anything outside `.claude/`, `.tripwire/`,
     `CLAUDE.md`, `CLAUDE.md.bak`, `.git/info/exclude` mutations).
   - **Scaffold noise** (everything else).
3. Stage only agent-authored paths. Commit with message
   `WIP({sid}): preserved before cleanup`. Push to `origin/<branch>`.
4. Discard scaffold-noise (it'll be re-rendered on next spawn). Then
   proceed with the existing remove logic.

If the agent-authored set is empty, behave as today (skip dirty unless
`--force`). New flag `--cleanup-dry-run` (renamed from --dry-run if it
collides) prints the partitioned tree without acting.

#### R4 — Spawn handles pre-existing remote branch

**File:** `src/tripwire/runtimes/prep.py:resolve_worktrees_for_session`

Today `worktree_add` creates `<branch>` from `<base_branch>` and
`_open_draft_pr` opens an empty marker commit + push. When
`origin/<branch>` already exists with commits beyond base, the push is
non-FF and the spawn aborts mid-prep.

Fix: before creating the branch, check for `origin/<branch>` via
`git ls-remote origin refs/heads/<branch>`. If present:

- Use `worktree_attach` (already exists for v0.12.1's `--resume`
  recreate) to attach the existing remote branch as the worktree, NOT
  a fresh-from-base branch.
- Skip the empty `session({sid}): start` marker commit (it's a no-op
  when there's substantive history).
- Skip the initial push (the remote already has these commits).
- Still attempt `gh pr create --draft` for the worktree branch only if
  no PR exists yet (`gh pr list --state all --head <branch> --json number`
  empty).

This makes "preserve partial work + fresh agent conversation" a
first-class flow. PM handoff #6 step 12 (destroying remote branch state
to unblock spawn) becomes unnecessary.

#### #18 — Cleanup deletes the local branch ref in parent clones

**File:** `src/tripwire/cli/session.py:cleanup_session_worktrees`

After `git worktree remove`, the parent clone retains the local
branch ref `refs/heads/<branch>`. Fresh spawn then errors with
"branch already exists in parent clone" until the operator runs
`git branch -D` manually. This bites the recovery flow at step 9 of
PM handoff #6 and is a 5-line addition:

```python
subprocess.run(
    ["git", "-C", str(clone_path), "branch", "-D", branch],
    check=False,  # branch may already be gone; not fatal
    capture_output=True,
)
```

The branch is reconstructible from origin if needed, so destruction
is safe.

#### R6 — `--resume` valid from any state with `claude_session_id`

**File:** `src/tripwire/cli/session.py:session_spawn_cmd` (~line 569)

Today the `--resume` precheck rejects unless `session.status` is
`paused` or `failed`. Replace with: `--resume` is valid iff
`session.runtime_state` is populated AND
`session.runtime_state.claude_session_id` is non-empty AND
`session.runtime_state.worktrees` is non-empty.

The status check moves to a **post-resume normalise**: after a
successful runtime restart, the executor flips session status to
`executing` via `execute_transition` with the appropriate
`*-to-executing` route. The route handles preserve_fields and any
side-effects. If no such route exists from the current status, that's
a transition_not_reachable error surfaced to the operator.

### WS5 — Multi-skill issues (issue.skills)

**Files:** `src/tripwire/models/issue.py`, the issue template under
`templates/issues/`, the validator's session-issue coherence check.

Today an `Issue` declares a single `agent: str` field which is read at
session-creation time to determine the session.agent. When a session
legitimately bundles cross-domain work (e.g. backend middleware +
frontend banner state in the billing-gate session) there's no shape
in the spec for "this issue benefits from these skills."

**Schema:** add `skills: list[str] = Field(default_factory=list)` to
`Issue`. `agent` is preserved (back-compat) and continues to designate
the dominant skill; `skills` is the explicit list. Resolution: at
session-create / spawn-prep time, the union of `session.agent` and
every member issue's `agent + skills` is the set of skills loaded into
the worktree.

**Validator:** issue-triage #10's coherence lint
(`coherence/issue_skill_not_in_session_skills`): if any
`issue.skills` or `issue.agent` is not in the session's effective
skill set, surface a queue-time warning with the fix-hint:
"either rename `session.agent` to a multi-skill alias (e.g.
`multi`) or set `session.skills: [...]` to declare bundling
explicitly." Severity: warning, not error — sometimes the agent
genuinely shouldn't load every skill (e.g. a coding-only sprint
where frontend issues are deferred).

**Spawn:** `prep.copy_skills_into_worktree` now takes a union
collected from `session.agent ∪ session.skills ∪ Σ issue.agent ∪
Σ issue.skills` so the worktree gets every skill any participating
issue might need.

### WS6 — PM context priming + scope-rejection workflow step

**Files:** `src/tripwire/runtimes/prep.py:render_claude_md_from_template`,
`src/tripwire/templates/agents/claude.md.j2` (or wherever the CLAUDE.md
template lives), `src/tripwire/templates/skills/project-manager/SKILL.md`.

**Pin PM skill to top of CLAUDE.md.** When a spawn's effective
skill-set includes `project-manager` (i.e. the agent is acting as a
PM), the rendered CLAUDE.md prepends the contents of
`templates/skills/project-manager/SKILL.md` immediately after the
project header — before any session-specific or issue-specific
context. This means every PM agent reads the skill as the first
load-bearing prose in its conversation, not as an on-demand lookup.

Implementation: pass `is_pm_agent: bool` to the Jinja template;
inside the template, conditionally `{{ pm_skill_md }}` at the top.
The renderer reads the skill content at render time so per-project
customisations of the skill propagate without code change.

**Add scope-rejection workflow step.** New section in
`templates/skills/project-manager/SKILL.md` — placed near the top of
the **monitoring** workflow because that's the loop where it fires
— covering:

1. **Detection signal.** Any of: an agent posts "this is outside my
   scope," "I'll defer X," or completes a session that was bundled
   with multiple issues but only addressed a subset. The PM is
   responsible for noticing.
2. **Mandatory response.** Pause the agent (via
   `tripwire session pause`). Do NOT rubber-stamp. Do NOT continue
   monitoring as routine.
3. **Inbox write.** `tripwire inbox add --kind scope-rejection
   --session <sid> --issue <key> --note "<agent's stated reason>"`
   so the user sees it without having to scrape monitor output.
4. **Wait for user.** The PM does not auto-reassign, auto-defer,
   or auto-split. It surfaces the decision and stops. The user
   replies via the inbox; the PM resumes the loop after the user
   has either confirmed the deferral or directed re-scoping.

**Add to the "rationalisations to catch" red-flag table** (issue
#3): the row from the issue-triage:

| Agent thought | Reality |
|---|---|
| "The agent's scope-prune sounds reasonable, I'll continue monitoring" | The agent dropping a tracked issue is a scope edit. Pause and escalate via the inbox. |

If `tripwire inbox add` doesn't exist yet, ship a minimal
implementation: append a JSON-L row to `.tripwire/inbox.jsonl` with
the kind, session, issue, note, and timestamp. The full inbox
workflow runtime (the `inbox-handling` workflow in the reference-only
docs) is out of scope; we just need the write-side primitive.

### WS7 — Spawn-prompt reframe + agent-mismatch lint (issue-triage #1, #10)

**Files:** `src/tripwire/runtimes/prep.py` and the kickoff-prompt
template, `src/tripwire/core/validator/checks/coherence.py` (or
adjacent), `src/tripwire/cli/session.py:session_check_cmd`.

**Reframe the spawn prompt.** The current "You are the
{session.agent} agent for session <sid>" framing reads as identity
and causes self-restriction (issue #1: billing-gate's agent dropped
KBP-65 citing "outside my agent scope"). Replace with:

> This session loads the {{ skill_list }} skill(s) — these provide
> references and tool hints for the work. **Skill loading is not a
> scope gate.** Your scope is everything declared in the linked
> issues (see plan.md and the issue files). If an issue requires a
> capability you don't have a skill for, say so explicitly in your
> next message — do NOT silently drop or defer the issue.

The kickoff prompt's tone shifts from identity-claim ("you are") to
capability-statement ("this session loads"). The closing instruction
is the explicit anti-rationalisation guard.

**Add agent-mismatch lint at queue time** (issue #10). New
validator: `v_session_issue_agent_coherence`. Fires when
`session.agent` (or `session.skills`) does not include every
`issue.agent` for member issues. Wired into the
`planned-to-queued` route's `controls.tripwires` and surfaced via
`tripwire session check`. Severity: warning. Fix-hint cites WS5's
multi-skill resolution.

### WS8 — Kickoff-prompt deferred-tool surfacing (issue-triage #16)

**File:** the kickoff-prompt template under
`src/tripwire/templates/` (location TBD by the file structure).

Pre-load the existence of `Monitor` and `TaskStop` tools in the
spawn-time kickoff prompt. The agent doesn't need the schemas (those
are still loaded on-demand via `ToolSearch`), just awareness. Two
sentences in the kickoff:

> If you start a long-running command (test suite, build, etc.) and
> the foreground bash tool reroutes to a background task, use
> `Monitor` to subscribe to its progress. If a background task is
> stuck (no output for >2 min, process still alive), use `TaskStop`
> to kill it before it accumulates with retries.

This gives every agent the recovery vocabulary without requiring
discovery during a stuck-loop.
